## Планирование анализ, идентификация проблем и поиск решений

### Проблемные места
1. Подняты только по одному инстансу сервисов и бд. При сбое сервиса он полностью будет неработоспособен, аналогично с БД
2. База данных работает на запись и на чтение, что создает большую нагрузку на базу
3. Нет кеширования, и все запросы идут всегда к БД, что также создает большую нагрузку на БД
4. Нет контроля загрузки очереди RabbitMQ, что влечет задержки в обработке, потеря данных или дублирование
5. На данный момент QA-инженер прогоняет E2E-сценарии вручную, что сильно замедляет работу
6. Нет наблюдаемости (мониторинга очередей, метрик времени этапов, алёртов), что усложняет поиск и локализация сбоев 
7. MES считает цену долго (до 30 мин), при росте входящего потока становится узким местом

### Инициативы, которые необходимы для устранения нежелательных ситуаций
1. Горизонтально масштабировать сервисы и БД для обеспечения бесперебойной работы систем
2. Настроить репликацию БД и перенаправить запросы с MES (дашборд) на чтение с реплики
3. Определить данные которые можно закэшировать, реализовать кэширование этих данных
4. Автоматизировать тесты, нанять еще одного QA-инженера
5. Нанять еще одного DevOps-инженер/SRE-инженера для обеспечения надежности функционирования систем, 
6. Обеспечить наблюдаемость: внедрить мониторинг, трейсинг, метрики, алерты
7. Внедрить API Gateway для внешних систем, настроить на нем политики доступа и управления трафиком (rate limit)
8. Внедрить паттерны Backpressure на прием новых заказов, чтобы снизить нагрузку на системы
9. Выделить в отдельный сервис тяжёлые вычисления (расчет стоимости изделий, обработка 3D)

### Приоритизация инициатив
1. Обеспечить наблюдаемость: внедрить мониторинг, метрики, алерты.
   Причина: быстрая реакция на проблемы, стабилизация SLA
2. Выделить в отдельный сервис тяжёлые вычисления (расчет стоимости изделий, обработка 3D)
   Причина: главное узкое место в процессе
3. Настроить репликацию БД и перенаправить запросы с MES (дашборд) на чтение с реплики, а также реализовать кэш для дашборда
   Причина: операторы должны быстро брать новые заказы, иначе п

### Целевая архитектура через полгода
* Системы масштабированы горизонтально, повышена отказоустойчивость
* Настроена репликация, запросы идут к реплике, база данных разгружена
* Дашборды работают от read-модели, также часть данных закэширована
* MES разделён на:
  Web/API слой (быстрые запросы UI, управление производством),
  Compute слой (расчет стоимости изделий, обработка 3D) - горизонтально масштабируемый сервис
* Настроен мониторинг, который выявлять проблемные места более быстро
* Внедрен API gateway для внешних запросов - rate limiting, квоты
* Реализованы механизм Backpressure для запросов через API и онлайн-магазин
* Релизы ускорены за счет авто тестов
