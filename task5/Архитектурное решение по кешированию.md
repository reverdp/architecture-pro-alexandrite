## Архитектурное решение по кешированию

### Мотивация
Кеширование позволит разгрузить MES DB и ускорить самые частые операции чтения для UI MES (дашборд и списки заказов):
* Дашборд "заказы в работе по статусам"
* Страницы/запросы "новые заказы" (самые горячие для операторов)
* Карточка заказа в MES
* Ответы API MES для внешних партнеров

Какие элементы системы включаем в кеширование:
* MES backend

Ожидаемый эффект для бизнеса и команды:
* Быстрее загрузка первой страницы MES (операторы видят новые заказы без ожидания БД)
* Меньше просрочек из-за операционных задержек: заказ быстрее обарбатывается оператором
* Устойчивость к росту нагрузки без немедленного масштабирования БД

### Предлагаемое решение
Основной выбор - серверное кеширование на стороне MES backend, 
поскольку проблема в первую очередь на стороне MES/БД (тяжёлые запросы, рост объёма, конкуренция чтений)
Хранилище кеша: Redis (in-memory distributed cache) как отдельный компонент

Паттерн кеширования Cache-Aside:
1. MES backend сначала читает из кеша
2. Если промах - читает из БД, кладёт в кеш и возвращает ответ
3. При изменениях статуса заказа MES обновляет данные кэша, путем записи в outbox события для последующей асинхронной обработки

Почему Cache-Aside:
* минимальные изменения в коде, легко использовать точечно
* проще управлять консистентностью: для новых заказов можно держать небольшой TTL и инвалидировать на события статусов
* отказоустойчивость: если Redis недоступен, система продолжает работать, читая из БД

|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------|
