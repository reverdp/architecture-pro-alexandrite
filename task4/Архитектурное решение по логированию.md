# Архитектурное решение по логированию

### План покрытия логами

#### Список необходимых логов с уровнем INFO:

**Shop**
  * создание заказа: timestamp, order_id, customer_id
  * загрузка файла с 3D-моделью изделия:  timestamp, order_id, customer_id, file_size
  * оформление заказа: timestamp, order_id, customer_id
  * запрос на расчёт цены: timestamp, order_id, request_id/message_id

**CRM**
  * изменение статуса заказа: timestamp, order_id, employee_id
  * публикация событий в MES: order_id, event_type, queue, message_id

**MES**
  * старт и завершение расчета стоимости заказа: timestamp, order_id, duration_ms, price
  * старт и завершение изготовления изделия: timestamp, order_id, operator_id
  * публикация событий в CRM: order_id, event_type, queue, message_id
  * внешние входящие запросы: timestamp, operation_type, user_id, request, response

**RabbitMQ**
  * publish: queue/exchange, message_id, order_id
  * consume+ack: queue, message_id, order_id, processing_ms
  * retry / DLQ: queue, message_id, order_id, result=retry|dlq

#### Другие уровни логирования

**WARN**
* повторная обработка/ретраи/дубликат запросов
* слишком долгое выполнение (например, расчёт цены > N минут)

**ERROR**
* Используем при невозможности выполнить какую либо операцию:
* не удалось посчитать цену
* не удалось записать статус в БД
* не удалось опубликовать/подтвердить сообщение
* 5xx на API, необработанные исключения

**DEBUG**
* Включаем только временно:
* при расследовании инцидента
* на ограниченном времени/сервисе

### Мотивация
**Что это даст компании:**
* быстрее решать инциденты и отвечать клиентам/партнёрам фактами
* уменьшить количество зависших/непонятных заказов за счёт быстрого выявления первопричин
* снизить нагрузку на поддержку (меньше ручной диагностики и эскалаций)
* ускорить выпуск исправлений (быстрее понять, что сломалось после релиза)
  
**Метрики, на которые повлияет внедрение логирования:**

Технические:
* MTTR (Mean Time To Recovery) — снизится: логи позволяют быстро локализовать сервис и причину ошибки.
* MTTD (Mean Time To Detect) — снизится: по централизованным ERROR/WARN и паттернам можно раньше замечать деградации.
* Доля повторных инцидентов одного типа — снизится: по логам проще делать RCA и закрывать первопричины, а не “лечить симптом”.

Бизнесовые:
* Доля просроченных заказов / количество претензий — снизится: быстрее обнаруживаем и устраняем “зависания”, меньше заказов уходит в долгую.
* Стоимость поддержки (время на тикет) — снизится: быстрее диагностика, меньше эскалаций на разработчиков.

**Приоритизация**
1. логирование INFO-событий "статус изменился/сообщение published/consumed/ack/dlq"
2. трейсинг HTTP внутри MES/CRM + проброс через RabbitMQ headers (order_id, message_id)

### Предлагаемое решение
В качестве хранилища логов предлагается использовать Loki
Поскольку уже используется Grafana для визуализации метрик, ее можно использовать и для просмотра логов через Loki
Сбор логов на каждом инстансе (агент) будет осуществляться с помощью Promtail
Ставим Promtail рядом с каждым приложением Shop API, CRM API, MES API и рядом с RabbitMQ (агент читает логи из stdout/файлов)

Преимущества такого решения:
* одна витрина (Grafana) для метрик и логов
* удобно связывать логи с метриками/алертами
* дешевле и проще, чем ELK

**Политика безопасности логов**
* Логи — внутренний ресурс. Публичного доступа из интернета нет
* Доступ через SSO/корп-учётку + RBAC
* Не пишем в логи: пароли, токены, ключи
* Маскирование чувствительных данных
* Логи разделяем по labels:
  * env = dev|release|prod
  * service = shop-api|crm-api|mes-api|rabbitmq
* Период хранения: prod: 30 дней, release: 14 дней, dev: 7 дней

### Алертинг
Отслеживание следующих событий:
* DLQ/retry detected: количество логов result=dlq или result=retry > 0 за 5–10 минут (по service/queue) - возможная потеря/зависание цепочки заказов
* level=error > X/мин по сервису - возможно падение какого либо сервиса
* published растёт, а consumed/ack почти нет (за окно 10–15 минут) - consumer отвалился или не успевает
* резкий рост событий создания/auth failures/4xx errors - возможно DDoS-атака
