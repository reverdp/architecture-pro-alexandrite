## Архитектурное решение по трейсингу

### План покрытия трейсингом
#### Где заказ может сломаться
1. B2C поток (онлайн-магазин)
* INITIATED → FILE_UPLOADED → SUBMITTED (Shop) - файл загружен, но заказ не сабмитнут
* SUBMITTED → PRICE_CALCULATED (Shop → MES) - запрос/сообщение на расчёт не дошло до MES, потеря/задержка в очереди, долгий расчёт.

2. B2B поток (партнёры через API)
* API user → (MES / входной API) создание заказа - заказ создан в одном месте, но не синхронизирован в CRM.

3. MES - CRM через RabbitMQ
* PRICE_CALCULATED (MES) → событие в CRM - событие не опубликовано/не подтверждено брокером;
* CLOSED (CRM) по событию от транспортной компании или вручную - внешний сигнал не обработан, закрытие не наступает

4. Производственные статусы внутри MES:
* MANUFACTURING_STARTED → COMPLETED → PACKAGING → SHIPPED - статус обновился в MES, но не ушёл дальше.

#### Системы, которые нужно покрыть трейсингом
Онлайн-магазин Backend (Java Spring Boot)
* входящие пользовательские операции
* исходящие вызовы/публикации в сторону MES/очереди

MES Backend
* приём задач/заказов (из Shop и B2B)
* операция расчёта стоимости
* смена производственных статусов
* публикация сообщений в RabbitMQ (в CRM)

CRM Backend
* подтверждение заказа
* закрытие заказа
* публикация/приём сообщений через RabbitMQ

RabbitMQ
* фиксация publish/consume/ack

### Мотивация

#### Без трейсинга команда вынуждена:
* вручную сопоставлять логи разных систем
* долго искать, где именно порвалась цепочка
* узнавать о проблемах поздно - через жалобы клиентов и партнёров

Трейсинг даёт сквозную видимость жизненного пути заказа: от первого запроса/сообщения до текущего статуса, включая очереди, внешние зависимости и ошибки. Это ускоряет диагностику и снижает вероятность повторения инцидентов

#### Метрики, на которые повлияет внедрение трейсинга
* Доля просроченных заказов - снизится за счёт устранения зависаний и потерь сообщений.
* p95/p99 времени переходов между статусами (например, SUBMITTED-PRICE_CALCULATED)
* Error rate (5xx/ошибки интеграций) - снизится, потому что первопричины ошибок видны в контексте трассы

### Предлагаемое решение
Трейсинг будет реализован с помощью внедрения OpenTelemetry и Jaeger

Компоненты:
* OpenTelemetry SDK - сбор телеметрии
* OpenTelemetry Collector — принимает трейсы по OTLP
* Jaeger - просмотр трейсинга

### Компромиссы
1. Проприетарные компоненты
Если часть MES/производственного контура использует проприетарный модуль (или библиотеку) 
для расчёта цены/обработки 3D, который не поддерживает OpenTelemetry или выполняется как отдельный процесс 
без доступа к коду, то мы не получим детальный трейс внутри расчёта
Компромисс: трассируем вокруг этого компонента, а детали диагностики — через логи/метрики

2. Высокая стоимость хранения и нагрузка при большом объёме трафика
Полный трейсинг (100% sampling) на высоком RPS, особенно после запуска B2B API, резко увеличит:
* объём данных (storage)
* нагрузку на сеть и backend трейсинга
* стоимость инфраструктуры
Компромисс: в prod используем sampling (например, 1–10%)

3. Дорогая доработка фронтенда
Frontend-трейсинг (Vue/React) полезен для UX, но требует отдельной интеграции и корреляции с backend trace,
Компромисс: сначала покрываем бэкенды + RabbitMQ, а фронтенд добавляем позже

### Безопасность
1. Модель доступа и роли (внутри компании)
* Включить SSO (корпоративная учётка) для UI трейсинга (например, через SAML)
* Ввести RBAC роли:
  * Support (read-only) — просмотр трейсов, поиск по order_id, без административных настроек
  * Admin/DevOps — настройка retention, sampling, интеграций, управление пользователями/группами
* Принцип минимальных привилегий: по умолчанию доступ закрыт, выдаётся по заявке
* Логировать события доступа к UI трейсинга

2. Сетевая безопасность (внутри компании)
* Закрыть компоненты трейсинга от внешнего интернета
* UI трейсинга и backend хранения — только во внутренней сети
* OpenTelemetry Collector принимает OTLP только от доверенных сервисов (Shop/CRM/MES)
В* ключить TLS между сервисами и Collector, а также между Collector и trace backend

3. Защита данных в трейcах (PII/секреты)
* Не писать чувствительное данные (пароли, токены, персональные данные)
* На уровне SDK включить фильтры: маскирование заголовков Authorization, Cookie, Set-Cookie

4. Хранение и срок жизни данных
* Ограничить хранение трейсов (например, 7–14 дней в prod) - достаточно для расследований, снижает риск утечки и стоимость.
